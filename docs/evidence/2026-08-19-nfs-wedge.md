# Evidence — the sulliwood NFS mount wedges, 2026-08-19 (neo)

Host: neo, macOS, 8 GiB RAM, Wi-Fi/EAP-TLS on `en0`. rclone 1.75.0 from the nix
store. Unit `dev.tinyland.gdrive-mounts.sulliwood-root`, backend `nfsmount`.

**Verdict: there are two distinct wedge classes, both invisible to the
supervisor, and both directly observed. In neither case does any process fail,
so `KeepAlive` never fires and nothing is ever logged. A restart fixes both,
which is why this repo now ships a watchdog.**

The mount wedged three times in one day. The operator's report each time was the
same: "Status flags: not responding, rclone alive, no error ever logged,
kickstart fixes it for a few hours."

---

## Class 1 — the mount stops answering while rclone stays healthy

Established from a SIGQUIT goroutine dump of PID 28806 (up 5h03m). The full
533-line dump and the surrounding log snapshot were preserved off-repo; the
load-bearing part:

```text
goroutine 117  go-nfs Server.Serve -> Accept        [IO wait, 303 minutes]
goroutine 119  go-nfs conn.serve -> readRequestHeader   (no request in flight)
goroutine 120  go-nfs conn.serializeWrites          [select, 9 minutes]
goroutine 25   drive.(*Fs).changeNotifyRunner       (mid changes.list)
goroutine 1    mountlib.(*MountPoint).Wait          [chan receive, 303 minutes]
```

31 goroutines. Exactly one accepted connection, zero handler goroutines, no
lock waiter anywhere. **rclone was not deadlocked — it was waiting for a client
that had stopped talking.**

Refuted by that dump, and not worth re-investigating: go-nfs handler-pool
exhaustion (no handler exists); VFS cache lock contention (no waiter, and the
cache dir held 0 files / 0 B); `--nfs-cache-handle-limit` churn (eviction
returns `NFS3ERR_STALE`, not silence); Drive token-refresh deadlock (the config
mtime shows a refresh succeeded 27 minutes earlier); a loopback retransmit storm
(the single connection was quiet); a goroutine leak (31 is nominal). The cache
SSD was independently exonerated at 262 MB/s measured during a wedge.

### The mismatch that causes it

```console
$ nfsstat -m
/Users/jess/GDrive/sulliwood from localhost:/
     NFS parameters: vers=3,tcp,port=57284,mountport=57284,hard,nointr,
       nodumbtimer,timeo=10,rsize=32768,wsize=32768,readahead=16
     Status flags: 0x2,not responding

$ sysctl vfs.generic.nfs.client.initialdowndelay vfs.generic.nfs.client.nextdowndelay
vfs.generic.nfs.client.initialdowndelay: 5
vfs.generic.nfs.client.nextdowndelay: 30
```

| layer | tolerance for a slow backend |
|---|---|
| macOS NFS client | **~5 s**, then the mount is marked dead |
| rclone `--timeout` (IO idle) | 5 m |
| × `--low-level-retries 10` | up to **50 m** on one operation |

Confirmed slow Drive I/O on the wedged PID, from kernel TCP summaries:
`897.962 s`, `270.713 s` ending in `so_error: 54` (ECONNRESET), `180.417 s`,
`91.822 s`, `84.771 s`. Any operation over 5 seconds kills a mount that rclone
still considers perfectly healthy, and `hard,nointr` then makes the dead state
bistable — callers block forever and cannot be signalled out.

### The flag flaps, which is why one failed probe must never trigger a restart

Sampled every 5 s against the live mount, read-only:

```console
$ nfsstat -m | awk -v p=/Users/jess/GDrive/sulliwood \
    '$1==p{s=1} s&&/Status flags:/{print $3; exit}'
```

```text
2026-08-20T00:18:04Z  94104  0x2,not responding
2026-08-20T00:18:24Z  94104  0x0
2026-08-20T00:19:15Z  94104  0x2,not responding
2026-08-20T00:19:25Z  94104  0x0
2026-08-20T00:20:00Z  94104  0x2,not responding
2026-08-20T00:20:10Z  94104  0x0
2026-08-20T00:21:22Z  94104  0x2,not responding
2026-08-20T00:21:37Z  94104  0x0
2026-08-20T00:21:42Z  94104  0x2,not responding
```

Five transitions in under four minutes, on one instance, clearing on its own
each time. **A watchdog that acted on a single sample would restart this mount
continuously.** Hence `watchdogFailureThreshold` has a schema minimum of 2, and
`watchdogIntervalSec` must stay well above the flap period.

## Class 2 — rclone alive, NFS port still listening, nothing mounted at all

Observed directly at 00:35Z, same day, on the instance that replaced the one
above. This is the class that matches "no error ever logged" most literally.

```console
$ ps -o pid,lstart,etime,command -p 94104
  PID STARTED                      ELAPSED COMMAND
94104 Wed Aug 19 19:49:23 2026       46:03 …/rclone nfsmount gdrive-sulliwood: …

$ mount | grep GDrive
(nothing mounted)

$ nfsstat -m
(no output — no NFS mounts on the host)

$ lsof -nP -p 94104 | grep -i listen
rclone 94104 jess 9u IPv4 … TCP 127.0.0.1:57284 (LISTEN)

$ ls -ld /Users/jess/GDrive/sulliwood
drwxr-xr-x  2 jess  staff  64 Aug 18 05:32 /Users/jess/GDrive/sulliwood

$ launchctl list dev.tinyland.gdrive-mounts.sulliwood-root | grep PID
	"PID" = 94104;

$ wc -l ~/Library/Logs/tinyland/gdrive-mounts.sulliwood-root.err.log
     552
```

rclone up 46 minutes. Still listening on the NFS port the vanished mount was
pinned to. The mountpoint is a bare, empty directory. **The err log has not
gained a line since 20:04:17** — 31 minutes of nothing.

### Why nothing ever recovers it

SIGQUIT to the same PID, 260 new lines, 19 goroutines:

```console
$ kill -QUIT 94104   # dump lands on the unit's stderr — launchd appends, never truncates
```

```text
goroutine 1   mountlib.(*MountPoint).Wait          [chan receive, 45 minutes]
goroutine 40  drive.(*Fs).ChangeNotify.func1       [select]
goroutine 27  vfs.(*VFS).signalHandler             [select, 45 minutes]
goroutine 66  os/signal.signal_recv                [syscall, 45 minutes]
…GC workers, finalizer, GOMAXPROCS updater…
```

Compare with class 1: **every go-nfs goroutine is gone.** No `Server.Serve`, no
`conn.serve`, no `serializeWrites`. The NFS server has stopped serving and its
listening socket is a leaked fd — while `mountlib.(*MountPoint).Wait` is still
blocked waiting to be unmounted.

So rclone never exits. So `KeepAlive = { SuccessfulExit = false }` never fires.
So launchd is perfectly happy, forever. **No supervisor can detect this by
watching the process, because the process is fine.** Only something that asks
the mount table can.

### The restart is the cure, and it is fast

After the SIGQUIT, launchd respawned the unit and the mount came back:

```text
t+10s mounted=1
$ nfsstat -m | tail -1
     Status flags: 0x0
```

Ten seconds, unattended, healthy. That is precisely the sequence the watchdog
now performs on its own.

### …and it recurs in minutes, not hours

The replacement instance was checked again twelve minutes later:

```console
$ ps -o pid,lstart,etime -p 71515
  PID STARTED                      ELAPSED
71515 Wed Aug 19 20:35:41 2026       12:18

$ mount | grep GDrive
(nothing mounted)

$ lsof -nP -p 71515 | grep -i listen
rclone 71515 jess 9u IPv4 … TCP 127.0.0.1:64165 (LISTEN)

$ tail -1 ~/Library/Logs/tinyland/gdrive-mounts.sulliwood-root.err.log
2026/08/19 20:37:17 NOTICE: Dangling shortcut "eBird Important Contacts" detected
```

Same class, same signature, on an instance twelve minutes old whose last log
line is at **two minutes**. So the mount survived roughly two minutes and has
been silently detached ever since. The operator's "kickstart fixes it for a few
hours" describes the *noticing* interval, not the mount's actual lifetime.

Two consequences for the watchdog's defaults:

- The 300 s mount-grace window would have cost five minutes on a mount that
  died at two. So the grace applies **only until the watchdog has seen the point
  mounted once**; after that a disappearance is unambiguous and is acted on at
  the next two cycles. Detection drops from ~7 minutes to ~2.
- The 300 s restart floor is of the same order as the observed survival time.
  That is acceptable — it bounds a restart loop without hiding anything, since
  held wedges are still recorded — but it means the wedge record, not the
  absence of complaints, is the thing to read.

## What shipped as a result

| Finding | Change |
|---|---|
| rclone's stall window (up to 50 m) outlasts the NFS client's (5 s) | `ioTimeout 20s`, `connectTimeout 10s`, `lowLevelRetries 3`, `attrTimeout 5s`, `pollInterval 5m` |
| "No error ever logged" is a log-level artifact — rclone logs retries and pacer backoff at INFO | `logLevel INFO`; `statsInterval 0` so an unrotated log does not grow a stats block a minute |
| Both classes are invisible to the supervisor | a health-probe sidecar unit per mount |
| The status flag flaps on a ~15 s timescale | probe every 60 s, act only on 2 consecutive failures |
| A `hard,nointr` caller cannot be killed, so `timeout` cannot bound a probe | the probe abandons a hung call instead of waiting on it |
| Diagnosis needed a signal and a hand-read dump | rc API on a unix socket in the 0700 state dir; the watchdog captures `core/stats`, `core/pid`, `vfs/stats` before it acts |
| Class 2 leaves nothing mounted with the process alive | an unmounted point past the grace window counts as a wedge |
| `umount -f` can return EBUSY and the wrapper would mount on top of the corpse | the sweep is asserted; `exit 75` if the point is still mounted |

Left alone deliberately: `nfsCacheHandleLimit`, `vfsReadAhead`, `cacheMaxSize`.
The dump refutes all three as causes, and memory pressure is an aggravator, not
a trigger — there was no `memorystatus` kill of either wedged PID.

Not attempted, and still owed a bakeoff: softer mount semantics
(`--option soft --option intr --option timeo=100`) to remove the bistability at
its root, and pinning the NFS port with `--addr 127.0.0.1:<fixed>` so a restart
can never orphan a client. Both need `docs/evidence/TEMPLATE-mount-bakeoff.md`
run against a real mount before they are defaults.
